**Findings**
1. Let-go stops do not compose safely with the gripper worker. The executor explicitly says gripper I/O is single-owner in the worker thread, but `_halt()` calls `_release_gripper()` directly before clearing the mailbox or setting `_stop`, so the worker can still race that synchronous `move()` and can even resend the stale close target. This affects the Session-4 `veto_retry_cap` path and any tactile/wrench/hitbox let-go stop, so the documented “it opens the fingers itself” behavior is not reliable as written. Evidence: [phantom/deploy/executor.py:59](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:59), [phantom/deploy/executor.py:149](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:149), [phantom/deploy/executor.py:163](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:163), [phantom/deploy/executor.py:175](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:175), [phantom/deploy/executor.py:389](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:389), [phantom/deploy/executor.py:402](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:402), [docs/rig_session_v5.md:100](/Users/sannikov/GitHub/phantom/docs/rig_session_v5.md:100).

2. `k-seeds` selection and the terminal veto can act on different ACC beliefs for the same replan. `PhantomPolicy.replan()` gates the head-descent rejection using `pred.acc.p_evt[0]` from seed 0 before selection, but then returns `plan.p_evt` from the selected seed `j`; the veto later uses that selected-seed `plan.p_evt`. With `K>1`, seed ordering can therefore change which chunks survive selection even though the eventual close-mask/recovery logic is reading a different seed’s event probabilities. That is a real composition bug in the Session-4 bundle (`--terminal-veto --k-seeds 4`). Evidence: [phantom/inference/policy.py:256](/Users/sannikov/GitHub/phantom/phantom/inference/policy.py:256), [phantom/inference/policy.py:258](/Users/sannikov/GitHub/phantom/phantom/inference/policy.py:258), [phantom/inference/policy.py:271](/Users/sannikov/GitHub/phantom/phantom/inference/policy.py:271), [phantom/deploy/planner.py:429](/Users/sannikov/GitHub/phantom/phantom/deploy/planner.py:429), [docs/rig_session_v5.md:74](/Users/sannikov/GitHub/phantom/docs/rig_session_v5.md:74).

3. Stop-reason recovery is maskable on the Session-4 `veto_retry_cap` path. `executor.stop()` records `servo_stop_failed` only if no earlier stop reason won the first-writer race; `run_deploy` rebuilds RTDE control only for reasons in `_CONTROL_DEAD_REASONS`, and `veto_retry_cap` is not one of them. So if a `veto_retry_cap` episode also leaves the servo session stuck, the later `servo_stop_failed` is suppressed and the next episode skips `recover_control()`, even though the code comments say that rebuild is the required fix. Evidence: [phantom/deploy/executor.py:144](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:144), [phantom/deploy/executor.py:455](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:455), [phantom/deploy/executor.py:472](/Users/sannikov/GitHub/phantom/phantom/deploy/executor.py:472), [phantom/deploy/planner.py:579](/Users/sannikov/GitHub/phantom/phantom/deploy/planner.py:579), [phantom/scripts/run_deploy.py:146](/Users/sannikov/GitHub/phantom/phantom/scripts/run_deploy.py:146), [phantom/scripts/run_deploy.py:679](/Users/sannikov/GitHub/phantom/phantom/scripts/run_deploy.py:679), [docs/rig_session_v5.md:100](/Users/sannikov/GitHub/phantom/docs/rig_session_v5.md:100).
